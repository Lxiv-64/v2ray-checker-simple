# Xray Config Checker Simple

Автоматический сбор, многоэтапная проверка и поддержание актуального списка
рабочих конфигураций для **Xray** — версия «поставил и забыл».

Программа сама подтягивает подписки, прогоняет серверы через воронку
(пинг → реальное ядро → контрольный трафик), держит пул в порядке и отдаёт
результат одним текстовым файлом. Ничего настраивать не нужно: все параметры
создаются при первом запуске, а окно нужно лишь для того, чтобы посмотреть
статистику, добавить подписку или настроить внешнюю команду.

Это самостоятельный проект, выделенный из большого «Xray Config Checker».
Ядро проверки (пакет `app/`, лежащий рядом) входит в поставку, поэтому
**сторонних зависимостей нет** — нужен только Python 3.8+ с Tkinter, а для
сборки одного exe — PyInstaller.

```bash
python simple_main.py                 # окно
python simple_main.py --headless      # цикл без интерфейса
python tests_simple.py                # самотесты (офлайн)
```

> **Как создан проект.** Программа написана агентом (агентной системой
> разработки) с применением ИИ-модели **DeepSeek** — это ИИ/LLM-проект.
> Код прошёл встроенные самотесты, но перед использованием в ответственных
> задачах его стоит проверить самостоятельно.

> **Язык интерфейса.** Поддерживаются русский и английский. Язык выбирается в
> «Настройки» → «Интерфейс» → «Язык интерфейса» и применяется после перезапуска
> программы. Английский README — в [`README.md`](README.md), русский — здесь.

## Как это работает: «поставил и забыл»

Проверка многоуровневая: разбор share-ссылок, пинг, реальное ядро Xray-core /
sing-box, контрольный трафик.  Вместо ручного управления серверами работает
**автоматический бесконечный цикл**, а результат отдаётся одним текстовым
файлом.

```bash
# графический интерфейс (главное окно, вкладки «Списки и вставка», «Серверы»,
# «Внешние команды», «Настройки», «Журнал»)
python simple_main.py
python simple_main.py --tray            # свёрнутым в трей (как при автозагрузке)
pythonw simple_main.py                 # без окна консоли (или двойной клик по simple_main.pyw)
# повторный запуск не открывает второе окно — он поднимает уже работающее

# без интерфейса: цикл в консоли (Ctrl+C — остановка)
python simple_main.py --headless

# один проход по воронке и выход
python simple_main.py --once

# добавить список из файла в пул
python simple_main.py --import my_list.txt

# статистика пула
python simple_main.py --stats
```

### Что делает цикл

1. **Подтягивает подписки** раз в N часов (по умолчанию 6) и добавляет новые
   конфигурации в пул. Протоколы, отключённые в настройках (например Trojan),
   при импорте отбрасываются.
2. **Этап 1 — пинг.** Все «новые» проходят быструю проверку DNS/TCP. Список
   сразу сокращается на десятки процентов: такие серверы не тратят время ядра.
3. **Этап 2 — ядро.** Выжившие проверяются настоящим ядром (реальное
   рукопожатие TLS/Reality/WS/gRPC). Конфигурации, которые ядро в принципе не
   умеет собрать, помечаются как «не поддерживается» и больше не проверяются.
4. **Этап 3 — трафик.** Лучшие из лучших должны пропустить контрольный HTTP-запрос
   через туннель. Такой сервер сразу попадает в выходной файл.
5. **Плановое обслуживание.** Рабочие серверы раз в час проверяются пингом, раз в
   6 часов — полноценной проверкой трафика. Любая неудача **разжаловывает** сервер
   в «новые» и убирает его из выходного файла; сервер снова проходит воронку с
   нуля.

### Значения по умолчанию — заполнять ничего не нужно

При первом запуске создаётся `data/simple/settings.json` со всеми параметрами
сразу (интерфейс никогда не показывает пустых полей), а битые или пустые
значения «лечатся» при каждом старте: вместо них подставляется значение по
умолчанию, поэтому ни интерфейс, ни цикл проверки не могут сломаться из-за
незаполненного параметра.

| Параметр | Значение по умолчанию |
| --- | --- |
| Обновление подписок | 6 часов |
| Пинг рабочих серверов | 60 минут |
| Трафик рабочих серверов | 6 часов |
| Неудач подряд до перехода в «Не работает» | 5 |
| Пауза между попытками этапа | 15 минут |
| Удалять нерабочие автоматически | **выключено** — сервер остаётся в пуле со статусом «Не работает» |
| Срок статуса «Не работает» | 72 часа: потом запись автоматически убирается из пула (`0` — не удалять) |
| Запись `pool.json` | не чаще одного раза в 30 секунд (изменения копятся в памяти; `0` — писать сразу) |
| Сжатие пула | `simple_pool_gzip` (по умолчанию включено): файл `pool.json.gz` примерно в 6 раз меньше; посмотреть содержимое — 7-Zip/WinRAR или `python simple_main.py --pool-dump` |
| Не добавлять удалённые (автоудалённые) | 12 часов |
| Потоки: пинг / ядро | 128 / 8 |
| Порции: пинг / ядро / трафик | 512 / 48 / 24 |
| Тайм-ауты DNS / TCP / ядра / трафика | 4 / 4 / 12 / 8 с |
| Запасные цели контрольного запроса | включены |
| Протоколы для импорта | все, кроме **Trojan** (включается галочкой) |
| Автозагрузка ядра | включена (без ядра этапы 2–3 не работают) |
| Выходной файл | `data/simple/working.txt` |

Тайм-ауты 4/4/12/8 и отключённый Trojan взяты из практики — со стоковыми 3/3/8/5 медленные серверы
отваливаются раньше, чем успевают ответить.

### Политика неудач

- Каждая неудача этапа учитывается отдельным счётчиком (пинг / ядро / трафик) и
  повторяется не сразу, а через паузу (по умолчанию 15 минут) — неудачи
  «разнесены по времени».
- После **5 неудач подряд** на одном этапе сервер удаляется и попадает в список
  «исключённых»: он не возвращается из подписок заданное время (по умолчанию 12
  часов), поэтому удалённый мусор не тянется заново.
- Отсутствие ядра на машине — не неудача сервера: этапы 2–3 просто пропускаются,
  а записи остаются кандидатами.

### Удаление серверов, статус «Не работает» и чёрный список адресов

Здесь три разные вещи, которые легко перепутать:

| Что | Как попадает | Сколько живёт |
| --- | --- | --- |
| **«Не работает (проверен)»** — статус в пуле | сервер исчерпал попытки (`Неудач подряд до удаления`, по умолчанию 5) | живёт `Срок «Не работает»` (по умолчанию 72 часа), потом убирается из пула автоматически; вернуть в проверки раньше — кнопкой «Сбросить в «новые»» |
| **Автоматическое «кладбище»** конфигураций | то же событие, но **только если** включена галка `Удалять нерабочие автоматически` | `Не добавлять удалённые` (по умолчанию 12 часов), потом может вернуться из подписки |
| **Постоянный чёрный список адресов** | кнопка **«В чёрный список (не проверять)»** | бессрочно, пока не уберёте вручную |
| **Ручное пополнение чёрного списка** | поле «Добавить в чёрный список» на вкладке «Серверы»: ссылка на сервер, `host:port` или просто IP — тогда блокируются все порты адреса | бессрочно, пока не уберёте вручную |

Главное: **по умолчанию сервера не удаляются**. Сервер, не прошедший проверку,
получает статус «Не работает» и остаётся в таблице — его видно, и решение
принимается осознанно: удалить, внести адрес в чёрный список или вернуть в
проверки. Автоудаление, как было раньше, включается галкой «Удалять нерабочие
автоматически» в настройках (вместе с ним начинает работать и «Не добавлять
удалённые»).

Статус «Не работает» — терминальный: такие серверы больше не опрашиваются, поэтому
у них есть **срок годности** (поле «Срок «Не работает», ч», по умолчанию 72 часа).
Раз в пять минут цикл убирает просроченные записи — иначе пул из подписок рос бы
вечно (у тысячи мёртвых серверов `pool.json` занимает десятки мегабайт). Ноль в
этой настройке возвращает прежнее поведение: записи остаются, пока их не удалят
вручную. Свежие записи (в том числе с провалом вчера) не трогаются.

**Удаление и чёрный список — строго разные процедуры:**

* **Удаление** («Удалить выбранные», «Удалить по фильтру», «Удалить все
  конфигурации») — чистка рабочей области, сброс результатов: адреса в чёрный
  список **не** заносятся, сервер сможет вернуться из подписки;
* **«В чёрный список (не проверять)»** — адрес `host:port` уходит в постоянный
  список, из пула убираются все конфигурации этого адреса (даже с другим UUID),
  он больше **не добавляется** ни из подписок и файлов, ни из вставки (в импорте
  учитывается как «исключён») и **никогда не опрашивается** — то есть системы
  защиты и антивирусы его больше не видят.

Управление списком: фильтр состояний → **«Чёрный список адресов (не
опрашивать)»** (видны адрес, дата, причина) → **«Убрать из чёрного списка»**
по выбранным строкам; кнопка **«Очистить чёрный список»** убирает и адреса, и
автоматическое «кладбище».

Список хранится в `data/simple/pool.json` (ключ `blocked_addresses`) и переживает
перезапуск. Счётчики видны в статусной строке («Нерабочих N», «ЧС адресов M») и в
`simple_main.py --stats`.

### Сколько раз проверяется сервер и откуда берутся «десятки попыток»

Замерено инстументированным запуском на реальных серверах (Xray 26.3.27):

| Что происходит | Исходящих подключений к серверу |
| --- | --- |
| Один удачный тест трафика | **2** (1 рукопожатие + 1 контрольный запрос) |
| Один провальный тест трафика, запасные цели включены | **5** (1 рукопожатие + 4 запроса) |
| Тот же провальный тест, запасные цели выключены | **2** (1 рукопожатие + 1 запрос) |

То есть **за один тест трафика делается от 1 до 4 HTTP-запросов**, а не десятки.
Первым всегда идёт `traffic_url` из настроек; если он не ответил, проверяются до
трёх резервных целей (gstatic по HTTPS и HTTP, connectivitycheck). Переключатель
**«Пробовать запасные цели»** (вкладка «Настройки» → блок **«Политика повторных
проверок»**) выключает резерв — тогда запрос ровно один, и на провальном сервере
число подключений падает с 5 до 2 (время теста — с ~14 до ~7 секунд).

Дополнительно к этому в каждом проходе воронки сервер видит:

* **пинг** (этап 1) — одно TCP-подключение на каждый IP, который вернул DNS
  (у имени с несколькими A-записями их может быть несколько, попытка
  прекращается на первом успешном адресе);
* **рукопожатие ядром** (этап 2) — одна попытка на цель, по умолчанию их две
  (цель из настроек и `www.gstatic.com:80`); при отключённых запасных целях —
  одна;
* запуск **одного процесса ядра** на тест (второй появляется только в случае
  TLS-сертификата, не проходящего строгую проверку).

Число «десятков» набирается не за один тест, а во времени: при
`simple_max_failures = 3` и паузе `simple_retry_minutes = 15` нерабочий сервер
успевает получить до 3 проходов (пинг + ядро + трафик), плюс плановые проверки
рабочих серверов (пинг раз в 10 минут и трафик раз в час при текущих настройках).
Антивирус при этом считает **сетевые события**, а не «тесты»: отдельно
подключение, отдельно обращение к DNS, отдельно разбор трафика; у транспорта
`xhttp` один запрос вообще занимает два-три TCP-соединения (раздельные
up/down-потоки). Если параллельно запущена вторая копия проверяльщика на тех же
подписках, серверы проверяются дважды.

Итого: если встроенные резервы не нужны, снимите галочку **«Пробовать запасные
цели»** (меньше сетевых событий, но цель, заблокированная на стороне сервера,
будет выглядеть как нерабочий сервер), а «Пинг рабочих серверов» и «Трафик
рабочих серверов» можно увеличить — они задают частоту плановых перепроверок.

### Плановая перепроверка рабочих серверов (пачками)

Обычная проверка поднимает **отдельный процесс ядра на каждый сервер** — это
оправдано на этапе отбора (изоляция ошибок, точная диагностика, сертификатный
ретрай), но для планового подтверждения уже проверенных серверов избыточно.

Поэтому рабочие серверы подтверждаются иначе:

1. **Пинг как фильтр.** Перед дорогой частью все отобранные серверы проходят
   дешёвый пинг (DNS + TCP). Не ответившие обрабатываются обычными правилами
   уровня 1, и пачка за них не платит.
2. **Уровень 2 пропускается.** Рукопожатие ничего не доказывает про креденшелы
   (VLESS/VMess примут TCP/TLS даже с неверным ключом) — рабочим сервер делает
   только контрольный запрос, он и выполняется.
3. **Один процесс ядра на пачку.** В конфиг кладётся по одному локальному
   SOCKS-порту на сервер и правило маршрутизации «порт → сервер». Измерения на
   реальных бинарниках: процесс с 50 портами стартует так же, как процесс на
   один сервер (+1 МБ памяти). Xray и sing-box не смешиваются — это два пула.
4. **Доля рабочих за проход.** За один раз подтверждается только часть рабочих
   (`0.25` по умолчанию): остальные в этом проходе не проверяются вообще, поэтому
   сбой пачки не может оставить выходной файл без серверов.
5. **Подтверждение провала.** Если сервер в пачке не ответил, он проверяется
   ещё раз одиночным контуром — и статус понижается только при подтверждении.
   Так сбой процесса, локального порта или сети не «разжалует» рабочий сервер.

Настройки (вкладка **«Настройки»**, раздел «Политика повторных проверок»):

| Параметр | Смысл |
| --- | --- |
| Доля рабочих за проход | какую часть рабочих подтверждать за один проход (`0.25` — четверть) |
| Серверов в пачке | сколько серверов кладётся в один процесс ядра |
| Порог сбоя пачки | при какой доле провалов проход считается сбоем: результаты не применяются |
| Сетевой предохранитель | приостанавливать проверки при пропавшей связи |

### Что происходит при обрыве сети

Если связь пропала (слежка за сетью проверяет её раз в `Проверка сети, с`):

- круг не делает проверок вообще: ни пинг, ни ядро, ни трафик;
- результаты, полученные во время обрыва, **не применяются** — статусы серверов,
  счётчики неудач и расписание остаются прежними;
- то же срабатывает при «массовом провале»: если в пачке провалилась большая
  доля серверов (больше «Порога сбоя пачки»), это считается проблемой связи или
  ядра, а не серверов;
- в статусной строке и в подсказке трея видно «нет сети — проверки
  приостановлены», в журнале — соответствующая запись.

Предохранитель можно выключить («Сетевой предохранитель»), но тогда массовые
тайм-ауты снова будут засчитываться серверам как неудачи.

### Режимы этапов

- **Каскад** (по умолчанию): за один круг обрабатывается по одной порции каждого
  этапа — список быстро чистится пингом, а дорогие проверки ядром получают лишь
  небольшую часть выживших.
- **Фазы**: за круг этап доводится до конца — сначала весь пинг, затем всё ядро,
  затем весь трафик.

### Пустой круг, запись пула и размер `pool.json`

Тысячи серверов — это тысячи записей, и всё, что делается «на каждый круг» или
«на каждый сервер», заметно на диске и процессоре. Поэтому:

- **Индекс очереди.** Пул хранит минимальную дату готовности по каждому этапу.
  Если ближайшая запись ещё «спит» (пауза между попытками, плановый интервал
  рабочего сервера), выборка не делается вовсе: пустой круг не перебирает
  10 000 записей, а новый сервер попадает в проверку сразу — индекс пересчитывается
  только при изменении пула. Замер на пуле из 20 000 записей, ожидающих своей
  даты: 300 пустых выборок — **0.5 мс** вместо **4.2 с** полного перебора.
- **Пауза по факту работы.** Пока проверки идут, круг ждёт `Пауза цикла, с`. Если
  проверять нечего, цикл спит до ближайшей даты в очереди — не дольше 5 секунд,
  чтобы вставка из буфера и «Обновить списки» обрабатывались сразу.
- **Пул пишется пачками — это прежде всего про ресурс SSD.** `pool.json`
  переписывается целиком, и при тысячах серверов одна запись — это десятки
  мегабайт. Пока идут проверки, в пуле меняется почти каждый круг, а пауза цикла
  по умолчанию — 1 секунда: получалось до ~86 000 перезаписей в сутки, то есть
  **около 1.3 ТБ записи в день** на реальном пуле (9962 записи, 16.2 МБ;
  одна запись — 2 секунды). За месяцы непрерывной работы как службы это лишний
  износ диска при нулевой пользе: чаще, чем раз в полминуты, состояние пула всё
  равно никому не нужно. Теперь файл сбрасывается не чаще `Писать пул не чаще, с`
  (по умолчанию 30 секунд) и только если пул действительно менялся: максимум
  ~39 ГБ в сутки, а при 300 секундах — около 4 ГБ. Изменения при этом не теряются:
  они живут в памяти и обязательно сохраняются при остановке, выходе и импорте
  («Стоп» и закрытие окна пишут файл принудительно).
- **Одна копия ссылки.** В `pool.json` ссылка хранится только внутри данных
  конфигурации, а не ещё и отдельным полем: у vmess-ссылок длина превышает 300
  символов, и дублирование давало мегабайты лишнего. На том же пуле файл стал
  **на 15% меньше** (16.2 → 13.7 МБ), то есть каждая перезапись легче на 2.5 МБ.
  Файлы прежних версий читаются без изменений.
- **Срок годности статуса «Не работает»** (см. выше) не даёт пулу расти вечно:
  на том же пуле под автоочистку попадает больше половины записей (5412 из 9792
  нерабочих «лежали» дольше трёх суток).

### Выходной файл

Настройка **«Выходной файл» → «Что сохранять»** предлагает три варианта:

| Вариант | Файл | Для чего |
| --- | --- | --- |
| Список ссылок (txt) | `data/simple/working.txt` | по одной `vless://…` на строку, отсортированы по задержке; годится как обычная подписка |
| Конфигурация для v2rayN (json) | `data/simple/v2rayN.json` | готовая пользовательская конфигурация Xray для офлайн-импорта в v2rayN |
| Оба файла | оба | и то, и другое одновременно |

Файлы обновляются автоматически при любом изменении состава рабочих серверов;
кнопка **«Сохранить вывод»** перезаписывает их вручную, **«Открыть файл»**
открывает тот, который соответствует выбранному формату. Именно к этим файлам
позже подключается отправка на сервер или в Telegram-бота — отдельный слой,
который ничего не меняет в проверке.

### Импорт в v2rayN офлайн (JSON)

v2rayN умеет принимать офлайн только «пользовательскую конфигурацию» — полный
JSON-конфиг ядра, — поэтому наш JSON собирается именно в таком виде:

* `inbounds` — локальные **SOCKS 10808** и **HTTP 10809** (значения по умолчанию
  в v2rayN);
* `outbounds` — по одному outbound на каждый рабочий сервер (+ `direct`/`block`);
* `observatory` — измерение задержки каждого сервера (цель — та же, что у
  контрольного запроса в настройках);
* `routing` — правило «весь tcp/udp → балансировщик» со стратегией
  **leastPing**: ядро само направляет трафик через самый быстрый сервер.

`observatory` обязателен: без него `leastPing` не работает и ядро вообще
отказывается стартовать («not all dependencies are resolved») — проверено на
Xray 26.3.27, в том числе тем бинарником, который использует ваш v2rayN.

**Как импортировать:**

1. В v2rayN: **«Серверы» → «Добавить пользовательскую конфигурацию»**
   (Add custom configuration server).
2. В диалоге укажите наш файл
   `data\simple\v2rayN.json` рядом с программой (есть кнопка выбора файла);
   имя и порт записи — любые, они нужны только для подписи в списке.
3. Готово: в списке появится одна запись, внутри которой вся группа рабочих
   серверов с автоматическим выбором быстрейшего.

При каждом старте ядра v2rayN **копирует указанный файл целиком** и ничего в нём
не меняет, поэтому путь достаточно указать один раз — при следующем запуске
v2rayN подхватит уже обновлённый список. (v2rayN также принимает просто имя
файла, если положить его в свою папку `bin\config`, но тогда копию пришлось бы
обновлять вручную, поэтому лучше указывать полный путь к нашему файлу.)

Ограничение: **Hysteria2 и TUIC в JSON не попадают** — это протоколы sing-box, а
пользовательская конфигурация в v2rayN запускается ядром Xray. Такие серверы
остаются в текстовом списке ссылок.

### Как получить в v2rayN отдельные серверы, а не одну группу

Короткий ответ: **развернуть пользовательскую конфигурацию в список отдельных
записей средствами v2rayN нельзя** — так устроен клиент: для пользовательской
конфигурации он просто копирует ваш JSON целиком и не разбирает его (проверено по
исходникам: `CoreConfigHandler.GenerateClientCustomConfig` → `File.Copy`).
Отдельные записи даёт **штатный офлайн-импорт из буфера обмена**:

1. В нашем окне нажмите **«Скопировать рабочие»** на панели сверху.
2. В v2rayN нажмите **Ctrl+V** — это команда **«Серверы» → «Добавить сервер(а) из
   буфера обмена»** (`menuAddServerViaClipboard`). v2rayN создаст **отдельную
   запись на каждую ссылку**; имя берётся из подписи после `#` в ссылке.

Если при отдельных записях нужна групповая логика, у v2rayN есть свои штатные
средства:

* **«Серверы» → «Добавить policy group server»** (`menuAddPolicyGroupServer`) —
  группа-политика поверх уже добавленных записей (выбор быстрейшего и т. п.);
* **«Настройки» → «Полный шаблон конфигурации»** (`TbFullConfigTemplateEnable`,
  `menuFullConfigTemplate`) — в шаблон добавляются дополнительные outbounds,
  `routing.balancers` и правила с `outboundTag`; туда ложится ровно начинка
  нашего JSON. При необходимости сделаю отдельный файл-шаблон под этот режим.

Почему нельзя подсунуть наш JSON как подписку: v2rayN принимает в качестве адреса
подписки **только `http://` и `https://`** (в исходниках `IsValidSubscription`
проверяет `StartsWith(Global.HttpsProtocol)` / `StartsWith(Global.HttpProtocol)`),
локальный файл или `file://` не подойдёт. Захотите обновление в один клик —
достаточно выложить `working.txt` на любой веб-адрес (или поднять локальный
HTTP-сервер) и указать его как подписку; тело подписки может быть и в base64 —
v2rayN декодирует её сам.

### Умная вставка из буфера (Ctrl+V)

Выбирать кнопку не нужно: приложение само понимает, что лежит в буфере.

| Что в буфере | Куда попадает |
| --- | --- |
| конфигурации: `vless://`, `vmess://`, `trojan://`, `ss://`, `ssr://`, `hysteria2://`, `hy2://`, `tuic://` | сразу в пул серверов (и в проверку — «Запустить» или F5) |
| ссылка на подписку: `http(s)://…` | в источники (и тут же начинается загрузка) |
| путь к файлу со списком (`file://…` или существующий путь) | в источники как файл |
| base64-подписка (одна длинная строка) | распаковывается в конфигурации → в пул |
| смешанный текст | раскладывается по корзинам: ссылки в источники, конфигурации в пул |
| непонятный текст | остаётся в поле «Вставка по Ctrl+V» — его можно поправить и отправить кнопкой «Добавить в пул» |

Отчёт о разборе появляется под полем: сколько добавлено в источники, сколько
конфигураций принято (и сколько было повторов или битых строк), сколько строк не
распознано. Точно так же работают кнопка **«Вставить из буфера (с разбором)»** и
пункт меню правой кнопки в поле вставки; кнопка **«Из буфера»** в блоке
источников тоже понимает конфигурации (отправит их в пул, а не в источники).

### Внешние команды: куда-то отдать готовый список

Вкладка **«Внешние команды»** — это нейтральный слой автоматизации: программа не
знает про транспорт, а просто запускает **ваши** команды и скрипты в нужный
момент. Так можно заливать `working.txt` на VPS, отправлять в Telegram, в GitHub
(gist), в облако по rclone, в свой bat-файл, обновлять локальную папку — что
угодно, без привязки к конкретному сервису.

**Когда запускается** (триггер пресета):

| Триггер | Поведение |
| --- | --- |
| При изменении списка | после того, как выходной файл **реально перезаписан** (и не чаще «минимальной паузы») |
| По расписанию | раз в N минут, даже если файл не менялся |
| Только вручную | кнопкой «Выполнить сейчас» |
| При запуске автоматизации | нажата «Запустить» (включая автозапуск): поднять внешние сервисы |
| При остановке автоматизации | нажата «Стоп»: погасить приёмник, отправить итог |
| Круг проверок завершён | после каждого круга — даже если файл не изменился |
| Пропала сеть / Сеть восстановилась | по слежке за связью (см. «Окно, трей и сеть» в настройках) |

Одновременно выполняется **одна** команда, остальные ждут в очереди — всплеск
изменений не превращается в лавину запусков. Кнопка «Стоп» в шапке останавливает
проверки, но **не** гасит планировщик: команда «при остановке» должна успеть
выполниться, а события работают, пока открыто окно. В режиме `--once` команды
выполняются после разового прохода.

**Как увидеть, что и когда выполнялось.** Столбец «Последний запуск» показывает
точное время и давность («26.09 07:33 · 22 мин назад»), результат — рядом; под
таблицей, в блоке «Вывод последней команды», для выбранного пресета есть полная
метка запуска с секундами, длительность и вывод. Давность пересчитывается по
таймеру (раз в несколько секунд), даже если состояние пресетов не менялось,
поэтому «только что» не застывает в таблице. У пресетов в режиме «скрытый»
команда и вывод не показываются, но метка времени видна — она секретом не является.

**Подстановки в команде:**

| Подстановка | Значение |
| --- | --- |
| `{file}` | путь к файлу со списком ссылок (`working.txt`) |
| `{json}` | путь к JSON-конфигу для v2rayN |
| `{count}` | сколько рабочих серверов в файле |
| `{out_dir}` | папка, где лежат оба файла |
| `{name}` | имя пресета |
| `{time}` / `{date}` | время и дата запуска |
| `{host}` `{port}` `{user}` `{password}` `{remote_dir}` | поля «Профиля подключения» |

Значения подставляются как есть: если путь может содержать пробелы, берите
подстановку в кавычки (`scp "{file}" user@host:/var/www/`) — редактор предупредит
об этом в предпросмотре. Путь к скрипту в кавычки заключается автоматически.

**Готовые примеры** (кнопка «Примеры…» создаёт из них пресет, дальше правится как
обычный):

```bat
:: 1. Залить на VPS по ключу (порт из профиля; у scp флаг -P, у ssh -p)
scp -P {port} -o BatchMode=yes -o ConnectTimeout=15 "{file}" {user}@{host}:{remote_dir}/working.txt

:: 2. Залить по паролю (pscp из PuTTY) и атомарно подменить файл
pscp -batch -pw "%COMMAND_PASSWORD%" -P {port} "{file}" {user}@{host}:{remote_dir}/working.tmp && plink -batch -pw "%COMMAND_PASSWORD%" -P {port} {user}@{host} mv -f '{remote_dir}/working.tmp' '{remote_dir}/working.txt'

:: 3. Готовый скрипт: загрузка + проверка sha256 + атомарная замена
scripts\upload-verify.cmd "{file}" {host} {port} {user} {remote_dir}

:: 4. Отправить файл в Telegram-бота (токен — в поле «Пароль», chat_id — в «Пользователь»)
curl -sS --fail --max-time 120 --proxy socks5h://127.0.0.1:10808 -F chat_id=123456789 -F document=@"{file}" "https://api.telegram.org/bot{password}/sendDocument"

:: 5. Приватный gist на GitHub (один раз: gh auth login)
gh gist create "{file}" --desc "working {date} {time}"

:: 6. Облако через rclone (реквизиты — в его собственном конфиге)
rclone copy "{file}" myremote:/pub/ --sftp-host {host} --sftp-user {user} --sftp-port {port}
```

### Работа как служба: иконка в трее и сворачивание

Программа задумана как бесконечно работающая служба, поэтому окно можно убрать с
панели задач, а автоматизация продолжится. В **«Настройках» → «Окно, трей и
сеть»**:

| Настройка | Что делает |
| --- | --- |
| Иконка в трее | иконка рядом с часами; по умолчанию включена |
| Закрывать окно в трей | крестик окна убирает его в трей (выход — через меню иконки) |
| Сворачивать в трей | кнопка «свернуть» тоже убирает окно с панели задач |
| Следить за сетью | источник событий «Пропала сеть» / «Сеть восстановилась» |
| Проверка сети, с | как часто проверять связь (по умолчанию раз в 30 секунд) |

Как это выглядит в работе:

* **галочки этого раздела применяются сразу** и сразу сохраняются в настройки —
  нажимать «Сохранить настройки» не нужно (раньше без этого шага поведение
  оставалось прежним: крестик спрашивал про остановку цикла, а «свернуть»
  оставляло окно в панели задач);
* **крестик** окна убирает его в трей без вопросов: приложение продолжает
  работать, окно исчезает и из панели задач;
* **кнопка «свернуть»** (и сворачивание окна любым способом) при включённой
  галочке тоже уходит в трей;
* при **первом** сворачивании иконка показывает всплывающую подсказку
  «Программа продолжает работать» — чтобы не пришлось искать окно;
* **двойной клик** по иконке (или пункт «Показать окно») возвращает окно;
  повторный клик прячет его;
* **правая кнопка** по иконке открывает меню: показать окно, «Запустить»,
  «Пауза / продолжить», «Остановить», «Сохранить вывод», «Выход» — те же
  действия, что и кнопки в шапке. Именно пункт **«Выход»** завершает программу
  (крестик при включённой галочке этого не делает);
* подсказка иконки показывает состояние: `работает, круг 12, рабочих 172`
  (и `· нет сети`, если связь пропала);
* трей реализован на `ctypes` (`Shell_NotifyIcon`) — никаких внешних библиотек;
  если иконку создать не удалось, приложение сообщит об этом и закроется
  обычным способом (сворачивать будет некуда).

Слежка за сетью — минималистичная: короткий TCP-коннект к двум публичным
адресам раз в интервал (две неудачи подряд = «сеть пропала»). Это даёт
автономному агрегатору события для команд: например, переключить выходной файл
на резервный сервер или отправить уведомление.

### VPS с нестандартным портом и паролем

Такое подключение (`ssh user@203.0.113.10 -p 11111` плюс пароль) описывается в
пресете обычными подстановками — **нестандартный порт проблемой не является**,
`{port}` просто подставляется в нужный флаг. Нюансы только два:

1. **Буква флага зависит от программы:** у `scp` порт — заглавная `-P`, у `ssh` —
   строчная `-p` (у `pscp`/`plink` — тоже `-P`). Опечатка приводит к «не удалось
   соединиться», поэтому в примерах выше эти флаги расставлены правильно.
2. **Пароль нельзя передать в `ssh`/`scp`** — OpenSSH принципиально читает пароль
   только с терминала, никаких `-pw`/`--password` у него нет. Поэтому либо:

| Ситуация | Решение |
| --- | --- |
| Доступен ключ | ничего не надо: `scp -o BatchMode=yes` + `StrictHostKeyChecking=accept-new` (ключ хоста принимается автоматически, без висящего вопроса `yes/no`) |
| Только пароль | `pscp`/`plink` из PuTTY: `-batch -pw "%COMMAND_PASSWORD%" -P {port}` — пароль подставляет оболочка из переменной окружения, поэтому он не светится ни в журнале приложения, ни в тексте пресета |
| Нужны проверка и замена | готовый скрипт `scripts\upload-verify.cmd` (лежит в репозитории, вызывается относительно папки проекта): сам выбирает `pscp` (если задан пароль) или `scp` (ключ), заливает в `working.tmp`, сравнивает sha256 (или размер, если на сервере нет `sha256sum`) и только потом делает `mv` — клиент никогда не скачает половину файла. Самотест без сети: `upload-verify.cmd --selftest` |

Первый запуск с паролем и `-batch`: PuTTY откажется работать с незнакомым ключом
хоста (это и нужно — висеть на вопросе `Store key in cache?` скрипт не будет).
Один раз подтвердите ключ вручную (обычный `pscp` без `-batch`), либо передайте
отпечаток явно: `pscp -hostkey <отпечаток> ...`.

Обе формы секрета рабочие: `{password}` подставляет приложение, `%COMMAND_PASSWORD%`
разворачивает оболочка. Вторая предпочтительнее — пароль не попадает в текст
командной строки пресета, который хранится в настройках и виден в интерфейсе.

**Что проверяет предпросмотр** (блок «Предпросмотр» в редакторе пресета и
«замечание:» в отчёте проверочного запуска):

| Замечание | Причина |
| --- | --- |
| `неизвестные подстановки: {234234}` | собственное значение завернули в фигурные скобки — они только для встроенных подстановок (`{file}`, `{port}`…) |
| `%имя% — такой переменной окружения нет` | вписали значение (например, сам пароль) как `%пароль%`: для cmd это имя переменной, подставится пусто. Нужен `%COMMAND_PASSWORD%` |
| `в команде есть {host}, но поле «Адрес» профиля пустое` | команда ссылается на подстановку, а поле не заполнено |
| `порт в профиле должен быть от 1 до 65535` | опечатка в порту (например, 234234) |
| `значение {file} содержит пробелы — возьмите его в кавычки` | путь с пробелами не закавычен |
| `конфиг для v2rayN не ведётся…` | команда берёт `{json}`, а в настройках выбран формат «только список ссылок» |

**Скрытые пресеты (приватность прямо в интерфейсе).** В редакторе есть блок
«Приватность», в котором режим пресета выбирается одной из двух радиокнопок —
«Обычный» или «Скрытый» (одно из двух, одновременно их не включить). У скрытого
пресета:

* в таблице вместо текста команды стоит `(скрыто)`, а в имени — значок замка;
* панель «Вывод последней команды» по умолчанию показывает только пометку, что
  команда и вывод скрыты, а кнопка **«Показать вывод»** раскрывает их до смены
  выбранного пресета (то есть «до специального действия»);
* при открытии редактора командная строка и предпросмотр замаскированы; рядом с
  радиокнопками есть кнопка-тумблер **«Показать содержимое»** — она снимает маску
  только в этом окне и на время работы с редактором, режим пресета при этом не
  меняется (у обычного пресета она заблокирована: скрывать нечего). Закрыли окно —
  открыли снова: содержимое опять скрыто;
* в журнал вместо команды и хвоста вывода пишется
  `команда скрыта (пресет помечен как скрытый)` — случайный скриншот окна или
  журнала ничего не выдаёт.

Пароль и адрес сервера маскируются в любом случае, а сам вывод хранится только в
локальном `data/simple/settings.json`, который в git не попадает.

**Надёжность и безопасность**

* пароль из профиля **не попадает в журнал** — в интерфейсе и логе он заменяется
  на `***`, а команда дополнительно получает его как переменную окружения
  `COMMAND_PASSWORD` (надёжнее всего держать секреты в самом скрипте, в `~/.ssh`
  или в конфиге rclone);
* команды запускаются **без окна консоли**; используйте неинтерактивные ключи
  (`scp -o BatchMode=yes`, `curl --fail --max-time …`), иначе запуск провисит до
  тайм-аута;
* по тайм-ауту процесс уничтожается **вместе с потомками** (`taskkill /T`);
* при ошибке выполняется до N повторов с паузой (тайм-ауты не повторяются);
* пресеты живут в `data/simple/settings.json` (ключ `simple_commands`) — там же
  лежат пароли профиля, файл не стоит передавать посторонним.

**Связка с подпиской v2rayN.** Пример №1 даёт готовую схему «обновление в один
клик»: команда заливает `working.txt` на ваш веб-адрес, а в v2rayN этот адрес
указывается как обычная **подписка** — клиент сам подтянет свежий список (v2rayN
принимает только `http(s)`-адреса и умеет декодировать base64).

### Сборка одного exe без консоли

Готовый монолитный файл собирается PyInstaller по spec-файлу в корне проекта.
Проще всего — скриптом `build-exe.cmd` (он переносит в `dist/` и иконку):

```bat
build-exe.cmd          :: быстрая пересборка: код и/или ico.ico изменились
build-exe.cmd clean    :: полная пересборка с нуля (PyInstaller --clean)
```

То же вручную (`--clean` нужен только при странностях кэша сборки):

```bash
python -m pip install pyinstaller
python -m PyInstaller XrayConfigCheckerSimple.spec --noconfirm
```

Результат — `dist\XrayConfigCheckerSimple.exe` (~11 МБ, один файл, окно без
консоли: в PE-заголовке подсистема `WINDOWS_GUI`).

Что попадает внутрь и что нет:

| В сборке | Снаружи |
| --- | --- |
| код `app/` и `simple/`, стандартная библиотека Python, Tkinter | `data/`, `logs/`, `tmp/`, `core/` — данные, настройки, ядра |
| сжатый архив модулей (`optimize=2`: без docstring-ов и assert-ов) | тесты (`tests*.py`), `.git`, `__pycache__`, файлы с серверами и командами с паролями |
| без UPX (`upx=False`) и без отладочного режима | SQLite и прочие неиспользуемые модули (исключены — нужен только код проверки) |
| иконка `ico.ico` — и как ресурс exe, и внутри архива (для окна и трея) | — |

Иконка указывается в spec (`icon='ico.ico'` плюс `datas=[('ico.ico', '.')]`): она
встраивается в exe, поэтому её видно в проводнике и на панели задач, а трей берёт
её из распакованной сборки (если файла рядом нет — используется системная).

Иконка должна быть **многоразмерной**: в списке файлов проводник запрашивает
16×16, на панели задач — 32×32, для крупных значков — 48…256 px. Если в `.ico`
лежит только один размер, Windows вместо иконки показывает стандартную заглушку
(именно так выглядит «exe со стоковой иконкой»). Собрать правильный файл из
одного изображения:

```bash
powershell -ExecutionPolicy Bypass -File scripts\make-ico.ps1
```

Скрипт берёт `ico.png` (или текущий `ico.ico`), делает кадры
16/24/32/48/64/128/256 и собирает ICO-контейнер (все кадры — DIB 32 бита с
прозрачностью, чтобы файл понимали и GDI+, и PyInstaller, и проводник).

Если exe уже пересобран, а проводник показывает прежний значок — это кэш иконок
Windows (он привязан к пути к файлу): нажмите `F5`, скопируйте exe под другим
именем или обновите кэш командой `ie4uinit.exe -show`.

Все свои данные приложение создаёт **рядом с exe** при первом запуске
(`data/simple/settings.json`, `pool.json`, `working.txt`, скачанные ядра в
`core/`). Для однофайловой сборки это обязательно: распаковка идёт во временный
каталог, который удаляется после выхода, поэтому путь берётся от папки exe
(`app.constants.base_dir()`). Итог: exe можно положить в любую свою папку —
лучше не в `Program Files`, чтобы было куда скачивать ядро.

Проверить чистоту сборки можно без запуска:

```bash
# список модулей внутри архива (тестов и data-* там быть не должно)
python -m PyInstaller.utils.cliutils.archive_viewer -r -l dist\XrayConfigCheckerSimple.exe

# подсистема PE: 2 = WINDOWS_GUI (без консоли)
python -c "import struct;d=open(r'dist\XrayConfigCheckerSimple.exe','rb').read();o=struct.unpack_from('<I',d,0x3C)[0];print(struct.unpack_from('<H',d,o+4+20+68)[0])"
```

Шаблон внешней команды `scripts\upload-verify.cmd` в exe не вшивается: если он
нужен, положите его рядом с exe — путь в пресете указывается относительно
рабочей папки приложения.

### Горячие клавиши и мелочи

Клавиши работают **независимо от раскладки**: окно слушает код клавиши, а не
символ. Это важно, потому что у Tk с нелатинскими раскладками беда — при русской
раскладке Ctrl+V приходит с другим keysym (а Ctrl+C и вовсе с ``'??'``), и
обычные привязки вида `<Control-v>` молча не срабатывают.

| Клавиши | Действие |
| --- | --- |
| Ctrl+V | разобрать буфер обмена: конфигурации — в пул, ссылка/файл — в источники (в поле ввода — обычная вставка) |
| Del | в «Серверах» — удалить выбранные, в «Списках» — удалить источник, во «Внешних командах» — удалить пресет |
| Shift+Del | в «Серверах» — внести адреса выбранных в чёрный список |
| Del (в фильтре «Чёрный список адресов») | убрать адрес из чёрного списка |
| Ctrl+A | выделить всё в активной таблице |
| Ctrl+C | скопировать ссылки (в «Серверах») или текст панели вывода (во «Внешних командах») |
| Insert | включить/выключить источник или пресет |
| F2 | изменить выбранный пресет |
| F5 | выполнить один проход немедленно |
| Esc | закрыть окно пресета без сохранения |

Если фокус стоит не на таблице (например, после клика по кнопке), команды
применяются к таблице активной вкладки; при открытом модальном окне пресета
клавиши ему и адресуются.

Правая кнопка мыши открывает меню действий там же, где есть таблицы и поля:

| Где | Что в меню |
| --- | --- |
| «Серверы» | проверить сейчас, сбросить в «новые», копировать ссылки, в чёрный список, удалить; в фильтре «Чёрный список адресов» — убрать из списка и очистить |
| «Списки и вставка» | включить/выключить источник, копировать значение, удалить источник, обновить подписки; в поле вставки — вырезать/копировать/вставить/выделить всё, добавить в пул, очистить поле |
| «Внешние команды» | добавить, изменить, дублировать, выполнить сейчас, включить/выключить, удалить |
| «Журнал» | вырезать/копировать/вставить/выделить всё, скопировать журнал целиком, очистить |

Меню и кнопки вызывают одни и те же действия: одного и того же можно добиться
клавишей, кнопкой и пунктом меню.

Таблица серверов обновляется **по месту**: при очередной проверке переписываются
только те строки, у которых изменились значения, а порядок строк пересматривается
не чаще раза в 1,5 секунды (когда работа остановлена — сразу). Поэтому выделение,
курсор и прокрутка не сбрасываются, а строки не прыгают под курсором во время
длинного круга. Поиск в шапке применяется с задержкой 0,25 с — иначе на каждое
нажатие клавиши пересчитывался бы весь список.

**Как окно помещается на экране.** Размер окна подгоняется под рабочую область
(`fit_window`): на экране 1366×768 окно открывается ниже «паспортных» 1080×760, а
не уезжает нижней частью за панель задач. Дальше работают четыре общих правила,
поэтому элементы управления больше не теряются при сужении окна:

* **Прокрутка содержимого.** Все вкладки («Списки и вставка», «Серверы»,
  «Внешние команды», «Настройки») прокручиваются целиком: полоса появляется,
  только когда содержимое выше видимой части, а если места хватает, содержимое
  растягивается на всё окно (таблица серверов по-прежнему занимает всю высоту).
  Колесо мыши над полем ввода или таблицей прокручивает их самих, и лишь на
  границе — вкладку: одно колесо, никаких конфликтов.
* **Перенос кнопок.** Панели кнопок (`AdaptiveBar`) при сужении перекладывают
  элементы на следующую строку вместо того, чтобы уезжать за правый край — и в
  шапке, и на вкладках, и в строке состояния.
* **Подсказки по ширине.** Тексты-подсказки переносятся по фактической ширине
  контейнера, а не по жёстким 980 пикселям, поэтому длинные абзацы не обрезаются.
* **Сетка настроек.** Поля настроек тянутся по ширине и сжимаются при нехватке
  места; два поля больше не могут оказаться в одной ячейке сетки (раньше так
  накладывались «Пауза между попытками» и «Удалять нерабочие автоматически»).

Проверить это можно и без глаз: `python tests_simple_gui.py` ставит окно на
минимальный размер и проверяет все вкладки.

- Пул хранится в `data/simple/pool.json` (включая «исключённых»), настройки — в
  `data/simple/settings.json`, поэтому оба файла переживают перезапуск.
- При закрытии приложение **гасит запущенные ядра** и не оставляет висящих
  процессов: оборванный на середине тест трафика не тянет за собой `xray.exe`
  и временные файлы в `tmp/`.
- Самотесты автомата состояний: `python tests_simple.py` (офлайн, без сети и ядер) —
  включая разбор буфера обмена, события-триггеры и слежку за сетью.
- Проверка интерфейса в реальном окне (вкладки «Внешние команды» и «Серверы»,
  редактор пресета, справка, ручной запуск, отрисовка таблицы серверов,
  контекстные меню, компоновка при минимальном размере окна, режим «скрытый» у
  пресета, умная вставка и работа с трей-иконкой): `python tests_simple_gui.py`.

## Технологический стек

- **Python 3.8+**, только стандартная библиотека (сторонних пакетов нет).
- **Интерфейс**: Tkinter / ttk; иконка в трее — на `ctypes`, без внешних
  библиотек.
- **Хранилище**: JSON-пул `data/simple/pool.json` (SQLite не используется).
- **Механизм проверки**: реальные ядра **Xray-core** и **sing-box**, запускаемые
  как подпроцессы с локальным SOCKS-входом.
- **Загрузка подписок и ядер**: `urllib`.
- **Параллельность**: `threading` + очереди задач.
- **Сборка exe**: PyInstaller — один файл без консоли (`build-exe.cmd`).
